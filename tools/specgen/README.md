# tools/specgen — Ultra kernel spec generator

Turns **a stock boot image + a 48 byte credential** into a Ultra spec (`offset|orig|repl` records)
that the on-device applier (`manager/.../ultrakernel/UltraKernelSpec` + `UltraKernelBuilder`) consumes.

Production generation delegates to `manager/ultrakernel` through `specgen/product.py`; its embedded
recipe uses generated bodies and target-specific metadata. `--self-check` and the Python recipe
below retain the historical k22 oracle. They do not exercise the current allocator or certify a
new kernel's boot. In particular, production `avc_info` resolves both the target's `avc_denied`
offset and its actual RET hook instead of carrying the oracle's packed AVC constants.

Today the only Ultra payload that has ever booted a device is `k22` for
`6.6.89-android15-8-g7e1f3c083cc6-abogki467167594-4k`, and its spec is an 18 line table of
**hard-coded file offsets** with one device's credential baked into three of the records. That is
why a different kernel, or the same kernel with a different credential, cannot be patched. This
tool removes both limitations:

| what was pinned | what the generator uses instead |
| --- | --- |
| 18 file offsets | a symbol name + a byte delta inside that symbol, resolved from the target kernel's own `kallsyms` |
| addresses inside the replacement blobs | relocations (`branch`, `movz/movk` displacement, `u32` symbol, `unsigned` struct offset) recomputed per kernel |
| the 48 byte credential in `panic`, `free_initmem` and the `0x45590` envelope | a declarative credential slot plus an init path derived from `credential[:16]` |
| `expectedKernelSha256` / `expectedBootSha256` | derived from the bytes just produced |

## Quick start

```bash
# 1. prove the generator reproduces the one payload that is device-proven
python tools/specgen/make_spec.py --self-check
#    add --verify-boot --java <jdk>/bin/java to also rebuild the boot through image-core.jar

# 2. generate a spec for any boot + any credential
python tools/specgen/make_spec.py --boot Ace6/boot.img \
    --credential 8eORURvE0cAkp3mlIzCuUsEJrr4OfbjKfT6RvkjeIP6aKm6r \
    --out k22.spec --receipt k22.json

# 3. a boot that is not the reference release is still generated, but labelled experimental
python tools/specgen/make_spec.py --boot other-boot.img --credential-file cred.txt \
    --out other.spec --receipt other.json
```

## Inputs

| input | required | notes |
| --- | --- | --- |
| `--boot` | one of | Android boot image, header v0–v4 (v4 is what the applier accepts). The kernel is read at `page_size` and decoded (`RAW_ARM64`, `GZIP`). `LZ4/zstd` are refused by name rather than guessed at. |
| `--kernel` | one of | a raw ARM64 `Image`, when the boot container is handled elsewhere |
| `--credential` / `--credential-file` | yes | exactly 48 ASCII `[A-Za-z0-9]`, the same contract as `MapleSuCredentialStore` / `UltraKeyProvisioning` |
| `--recipe` | no | defaults to `specgen/recipes/k22.json` |
| `--symbols` | no | a pre-decoded `offset<TAB>type<TAB>name` dump; otherwise the image is decoded here |
| `--require-release` | no | refuse to emit when the kernel release differs |

The credential is **not** read from the device. `maplesu-credential.bin` is AES-GCM ciphertext
under an AndroidKeyStore key, and the Ultra rootKey lives in SharedPreferences; both are
device-only. The credential must be explicitly supplied for the target image;
the generator does not read application-private storage.

## Outputs

`--out` is a spec file:

```
#generated by tools/specgen from recipe k22
#origin=GENERATED
#sites=18
#kernel=<release read from the image>
#key=<the credential>
<offset>|<orig hex>|<repl hex>
...
```

`#kernel=` and `#key=` keep the shipped grammar (`UltraKernelSpec.parse`). The leading `#` lines are
comments to the applier, so a generated spec drops into the existing asset layout unchanged.

`--receipt` is a JSON record with the derived digests, the site roles, the credential slot, the
symbol layout that was used, and `verification: verified|experimental`.

## Layout

```
make_spec.py             CLI, --self-check, receipt
derive_recipe.py         bootstrap: shipped k22 spec + reference Image -> recipes/k22.json
specgen/a64.py           the handful of AArch64 encodings the recipe needs
specgen/kallsyms.py      in-image kallsyms decoder (no external dependency)
specgen/recipe.py        recipe model, site resolution, relocation application
specgen/emit.py          applier-identical replay + spec text
specgen/bootimg.py       boot v4 header read + kernel decode
specgen/recipes/k22.json the recipe (18 records, 55 relocations)
```

## The recipe

`recipes/k22.json` is generated by `derive_recipe.py`, not typed by hand, and then frozen. Each
record is one of:

* **assembled** (9 of 18) — every byte comes from a rule, so there is no blob at all:
  `free_initmem` and `0x45590` envelopes (self/u32 symbol/init path/two carried constants/u16
  struct offset), the `panic` credential slot, and the one-instruction stubs
  (`movz x0,#1; ret`, `mov w0,wzr; ret`, `nop; nop`, `b <site>`).
* **template + relocations** (9 of 18) — the shellcode bodies whose instruction selection is the
  part of the craft we do not regenerate yet. Their offsets are still resolved by symbol; only the
  instruction bytes are carried, and every address inside them is a relocation.

Record order is semantic: the applier writes in file order, so the `0x8FCF7C` cave record is
written before the two 8 byte gates that live inside it.

### Relocation kinds

| kind | meaning |
| --- | --- |
| `branch` | `B`/`BL` to `symbol+delta`; imm26 recomputed from the target's own address |
| `imm64_delta` | `adr xN, .` + `movz/movk` + `add xN, xN, xM`, i.e. a 64-bit displacement to `symbol+delta`; the word count must match, so a value that no longer fits fails closed |
| `u32_target` | a 32-bit symbol offset stored as data (the envelope fields) |
| `u32_self` | a 32-bit reference to the record's own file offset |
| `u32_const` | a literal in the historical oracle; `0xE7280001` and `0x000B0062` together encode the old AVC descriptor |
| `avc_info` (production Kotlin recipe) | two tag bytes, the target's unaligned `u32 avc_denied` offset, and signed `i16` count satisfying `RET = avc_denied + count * 4 - 4` |
| `u16_struct` | `task_struct` field offset, read from the anchor symbol's own instructions (`prctl_get_seccomp`: `mrs xN, sp_el0` + `ldrsw xD, [xN, #imm]`, imm12 scaled by 4) |
| `init_path` / `credential` | the two device-specific printable slots |
| `word` | one assembled instruction (`ret`, `nop`, `movz`, `mov wzr`) |

## What this does and does not prove

**Proves** (on 6.6.89): the 18 records can be regenerated from `Ace6/boot.img` plus a credential
without any hard-coded file offset; the result is byte-identical to the shipped k22 spec, so the
applier's output is byte-identical too — kernel `287fbdd0…`, boot `47aa147a…`.

**Does not prove**: that the same recipe boots a *different* release. The relocations make every
address right, and the applier still verifies every record's pristine bytes, but the shellcode
bodies were compiled for 6.6.89. On another release the generator emits a spec marked
`experimental`; the missing piece is regenerating the code bodies (an assembler-level emitter)
rather than carrying them. That is the next work item, tracked in the report.
